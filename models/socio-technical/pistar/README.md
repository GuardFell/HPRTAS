# The i\* models, in piStar form

The Strategic Dependency and Strategic Rationale models of this folder - `sd-hprtas.json` and
`sr-hprtas.json` - converted into the model format of the [piStar](https://github.com/jhcp/piStar)
tool (version 2.1.0, iStar 2.0), so that the same drawings can be opened, read and edited in the
tool rather than only in the exported PDFs.

One file per drawing - the same drawings `istar_render.py` produces, plus the two whole-model pages:

| File | What it is |
|---|---|
| `sd-pathway.json` | the SD model on one canvas: the patient at the centre, the reception desk, the doctor and the specialist on the ring, and the seven dependums on the lines between them - for reading |
| `sd-all.json` | the same set of actors and dependencies as one union page, so tooling and lookups have the whole SD model in one file |
| `sr-patient.json`, `sr-receptionist.json`, `sr-doctor.json`, `sr-specialist.json` | one SR page per actor - 5, 6, 10 and 3 elements |
| `sr-all.json` | every actor at once: the four boundaries with their elements and links, and the seven dependencies drawn round them - the whole Strategic Rationale view on one canvas |
| `sd-overview.json` | the SD model again as the overview drawing a reader starts from |
| `sr-overview.json` | every actor's goals and tasks, with the links between them, and nothing else: no qualities, no dependencies. The activity view of the whole model |

Generated by `../tools/convert_istar_to_pistar.py` from the two source JSONs. The files are
generated, not edited: change the sources and re-run the converter, or edit a file in piStar and
keep the piStar file as the working copy, but do not hand-edit a file and then re-run the converter
over it.

```
python tools/convert_istar_to_pistar.py                       # regenerate all 9 files
python tools/convert_istar_to_pistar.py --check               # layout report, writes nothing
python tools/convert_istar_to_pistar.py --out DIR            # write the files somewhere else
```

## The exported PNGs

Each drawing has a PNG beside the other exports: `../exports/pistar-sd-<view>.png`,
`pistar-sd-all.png`, `pistar-sd-overview.png`, `pistar-sr-<actor>.png`, `pistar-sr-all.png` and
`pistar-sr-overview.png`, 9 in all, one per file here. They are written the way the tool writes
them - the paper's SVG, rasterised onto a white canvas at the model's own pixels (what **File → Save
image** does with **High resolution** and **Transparent background** both unchecked) - but driven
from a headless browser, because the tool itself has no command line:

```
node tools/export_istar_pngs.mjs                  # every drawing, into ../exports/
node tools/export_istar_pngs.mjs --only sr-doctor # one drawing
node tools/export_istar_pngs.mjs --scale 2        # piStar's 2x
```

It needs Node 22+ (its own `fetch` and `WebSocket`) and Chrome or Edge, and nothing to install; the
piStar tool is loaded from `piStar/tool/index.html` beside the repository unless `--tool` says
otherwise. So a model changed here means re-running the export, not exporting its page by hand.
`verify_hprtas_pistar.py` checks that every drawing still has its PNG.

## How the drawing is laid out

The SD model is drawn as a hub with a ring of actors: the patient sits at the centre - the view
names it as the hub, because every dependency the model states runs from the patient - the other
three actors sit on the ring in the order that leaves the fewest dependency lines crossing, and
each dependum sits on the line between the two actors it joins, lanes apart where several
dependencies run between the same pair. On an SR page the elements are in rows by kind, and each
row is ordered, and a link bent round what it would otherwise cross, so that linked elements sit
near each other. The placement is computed by `tools/istar_geometry.py`, the same code
`tools/istar_render.py` draws the PDF pages with.

## Opening a file

piStar is a browser tool with no build step and no installation: open its `tool/index.html`, then
**File → Load model from file** and pick one of these `.json` files. **File → Save model** writes the
same format back.

**The tool needs one local patch to open them.** piStar ships accepting only a file the browser
labels `text/plain`, and every browser labels a `.json` file `application/json`, so the unpatched
tool answers *"Sorry, this kind of file is not valid"* for a file it can read perfectly well. The
patch is one line in `piStar/tool/app/ui/ui.js` - the loader now accepts `text/plain`,
`application/json` and an empty type - and it is marked `[local patch]` where it sits, so a future
update of the tool can carry it forward. Without the patch the workaround is to copy a file to
`.txt` before selecting it: the extension is the only thing the check looks at.
`node tools/load_istar_pistar.mjs` is the check that this keeps working: it loads every file here
into the tool in a headless browser and fails on one the tool refuses.

piStar's own notation: a dependency is drawn as two lines through the dependum (the small tick at
the middle of a line is piStar's marker, not a symbol), a refinement is drawn with the arrowhead
(OR) or the end bar (AND) at the parent, a contribution with its label at the middle, and a soft
goal is called **Quality** and drawn as the cloud. Dependency types are not re-typed by editing the
file alone; do that in the tool (select the dependum, then the Properties panel).

## How the models were mapped

- **Actors.** `kind: "role"` → iStar **Role**; `kind: "agent"` → **Agent** (a concrete party, which
  is what an agent is; the patient and the reception desk are the concrete people the pathway
  names). SD views mark the actors `collapsed`, so they draw as the plain circles the notation
  uses; alt+click expands one in the tool.
- **Dependums and elements.** `goal` → Goal, `task` → Task, `resource` → Resource, `softgoal` →
  **Quality** (the cloud).
- **Links.** `means-end` → Or-refinement link, written from the means to the goal it serves, so the
  arrowhead lands on the goal, as in the exported diagrams. `decomposition` labelled `and` →
  And-refinement link (piStar draws its bar where the source notation draws a diamond, and writes no
  AND label). A contribution keeps its label; piStar knows `make`, `help`, `hurt` and `break` only,
  so `some+`/`unknown`/`equal` would become `help` and `some-` → `hurt` (the sources use `help`
  only).
- **A relation recorded at both ends is written once**, in the direction that reads as a means to an
  end: piStar allows only one refinement link between the same two elements, and its arrowhead has
  one direction. A `means-end` between two tasks - a task as one way of carrying out another - is
  recorded once, on the means.
- **The source metadata is kept**, as custom properties on the cells, visible in the properties
  panel: `Note` on a dependum; `Intent` on an actor; `AccountsFor` (the SD dependencies the element
  accounts for) on an SR element; `Source` and the model's own note on the diagram. The workshop
  model carries no requirement ids, so no `Rules` / `Requirements` properties are written.
- **A gap element** - a need the model does not meet - is drawn dashed in the exports. This model
  records none, so no node is tinted; the converter still tints one (`#EFD9D9`) and writes its
  `Gap` property if a future version introduces one.

## Links iStar 2.0 does not allow, and what happens to them

iStar 2.0's Table 1 allows a contribution link only into a **Quality**, and piStar enforces it: a
contribution into a hard goal makes the tool report "Invalid model" on load. The converter writes
such a link as a **means-end link** instead, which is what the i\* guide says it is: an
OR-refinement, "a particular way of fulfilling the parent goal". The link is drawn with the
arrowhead at the goal it serves rather than with a `help` label. The current model has no such
link - every contribution it states enters a soft goal - and the converter prints what it rewrote
if a source reintroduces one, so nothing is silently converted.

The contribution links that enter a soft goal are untouched and keep their `help` labels.

## What is not in these files

- **The legends** the exported PDF pages carry. piStar draws its own notation; the legend text is in
  `../README.md`, `../modelling-choices.md` and `../tables.md`.
- **The hub choice** is a model fact (`view["hub"]` in `sd-hprtas.json`), so the piStar drawing and
  the renderer's page put the patient at the centre the same way.
- **Long actor names are hyphenated inside the circle** ("Hospital ma/nagement"). That is piStar's
  own line breaking in a circle the tool does not let you resize; it is not something the file can
  set.

## Checking these files

```
python tools/verify_hprtas_pistar.py
```

It rebuilds every model from the sources and compares it with the file that is committed, checks
that the drawing is sound (nothing outside the canvas, no two cells touching, no dependum on an
actor), that every dependency and link resolves inside its own file, and that the claims this
README makes about the gap tints and the contribution links still hold - including that no link
written is one iStar 2.0 disallows. `convert_istar_to_pistar.py --check`
runs the layout half of that without the comparison.

```
node tools/load_istar_pistar.mjs
```

loads every file into the piStar tool itself, in a headless browser, and reports whether the
tool accepted it - the one check the static ones cannot make, because a file can be exactly
what the sources generate and still be one the tool will not open.

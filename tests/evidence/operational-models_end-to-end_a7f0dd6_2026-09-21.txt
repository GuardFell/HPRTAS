WHAT THIS RUN SHOWS
-------------------
`workers_end-to-end-smoke_813fea6_2026-09-21.txt` ran the workers against a purpose-built linear
fixture. This run uses the delivered models instead. Each scenario deploys the model and the forms,
starts the real workers, starts an instance, completes every user task the way a Tasklist user
completes it, and reads the path back from the Orchestration Cluster API. It is evidence that the
four models and the workers work together.

Scenario 5 is the refund. It is run after scenario 2 on purpose: the refund is recorded against the
payment reference scenario 2 settled with the simulated provider, so it exercises the refund worker
against a transaction that really exists rather than one the test assumed.

METHOD
------
1. deploy models/operational/core-1..4.bpmn (application/xml) and forms/*.form (application/json)
2. start the workers: `cd workers && npm start` (six workers registered on the gRPC gateway)
3. for each scenario, start the instance - from `POST /v2/process-instances`, or for the
   cancellation in scenario 5 from `POST /v2/messages/publication` on the message start event
4. complete each open user task through `POST /v2/user-tasks/<key>/completion` with the variables a
   validated form would supply
5. read the final state and the path back from `/v2/process-instances/search` and
   `/v2/element-instances/search`

WHAT THIS RUN ADDS OVER THE UNIT TESTS
--------------------------------------
The unit tests call the handlers directly. This run goes through the engine, so
it shows the parts the unit tests cannot reach: that the worker registers against
the gateway, that the gateway activates a job of the expected type for it, that
the variables it returns are merged into the process and the process continues,
and that a business error it raises is caught by the model.

METHOD
------
`test/fixtures/worker-smoke-test.bpmn` is deployed. It is a single linear
process, five service tasks wide, that calls each worker once:

  validate-referral -> check-appointment-availability ->
  check-treatment-availability -> process-payment -> send-correspondence

The fixture has an error boundary event on the treatment task catching
UNAUTHORISED_BOOKING_REQUEST. It is a test fixture, not a deliverable model; the
operational models live in `../../models/operational/`.

Two instances are then run and the path each one took is read back from the
Orchestration Cluster API, so the assertion is about the path rather than about
the workers' own claims.

LIMITATIONS OF THIS EVIDENCE
----------------------------
The fixture process is a straight line. It does not contain the funding and
payment gate, the two-week telephone contact path, the no-availability path or
any user task, so this run does not evidence those. They are covered, at worker
level, by the unit tests recorded in the other items in this directory, and they
must be evidenced again end to end against the operational model.

The smoke fixture is a second process definition in the engine alongside the
operational models. It is deployed by the test and is not part of the delivered
solution.

Reproduce with:
  cd workers && npm install
  (start the engine: camunda-runtime\start-camunda.bat)
  cd workers && npm run test:smoke

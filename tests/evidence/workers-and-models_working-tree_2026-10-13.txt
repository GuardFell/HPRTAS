The workers and the models, at all three levels, after the feedback pass
========================================================================

Version under test
------------------
The working tree on top of `aba6b29`, uncommitted at the time of the run: the feedback pass that
adds the record store, the input-validation policy, the appointment-confirmation outcomes, the
merging gateways and the end-to-end process. `git rev-parse --short HEAD` names the commit the
changes sit on and `git status` says which files differ from it - no hash is written here, because
the tree this describes is not a commit yet. The record store was a throwaway in-memory database
(`hprtas.dbUrl`), so none of the runs below left records behind.

Date: 2026-10-13.  Tester: automated, `cd workers && mvn test` and `cd workers && mvn test -Pengine`
against Camunda 8 Run 8.9.19 on this machine. The engine run was made twice, before and after the
diagrams were tidied; the transcript below is the second one, on the tree as it stands. The two runs
agree on every scenario.

------------
    cd workers

Result
------
    52 unit tests, 0 failures. The suite is the 43 the previous edition had, plus nine in
    `PersistenceTest` (the record store: a settled payment surviving a restart, the patient register
    lookups, the identity conflict, the rebooking supersede, the recorded channel preference and the
    information request that the reply updates) and one in `WorkersTest` (an empty optional list is a
    legitimate answer where an empty required one is not - `DEF-15`).

    14 engine tests, 0 failures, 0 errors: the two smoke scenarios and the twelve operational-model
    scenarios. The twelve are the nine the previous edition had, plus three added by this pass:

      * Scenario 10 - a declined confirmation in `core-2`. The contact is recorded as
        `declined_by_patient`, the appointment is released, the instance ends at
        `N_TB_AppointmentCancelled`, and no appointment letter is sent as though the appointment
        were going ahead. (`TC-22`)
      * Scenario 11 - a reschedule in `core-2`. The first contact is recorded as
        `reschedule_requested`, the change is recorded with the date the patient asked for, the
        booking is sought again (`N_TB_CheckAvailability` runs a second time, asserted by counting
        element instances rather than distinct ids), the second contact confirms, and the instance
        completes. (`TC-23`)
      * Scenario 12 - the pathway end to end. One `core-0` instance runs the documentation exchange
        (`core-5`), the referral, its decision and the first appointment (`core-1`), the treatment
        (`core-2`), the letter (`core-3`) and the follow-up (`core-4`), and the assertion is made on
        the tree of instances the engine recorded: every stage process is in it, and the root ended
        at `N_CO_PathwayComplete`. (`TC-24`)

    The transcript below is the tests' own report: every user task completed, with the variables it
    was completed with, and the element path each instance took. The JSON worker log lines are
    omitted here for length; where one carries a business error it says which variable was refused
    and why (`errorCode` and `errorMessage`).

What this run does not cover
----------------------------
- **No signed-in user.** Every user task is completed through `POST /v2/user-tasks/<key>/completion`
  with the variables a validated form would supply; no task is claimed from Tasklist and no role is
  enforced, which is `DEF-07` and `DEF-08`. The forms' own validation is checked separately, in the
  renderer library (`feedback-pass-static-checks-and-forms_working-tree_2026-10-13.txt`).
- **The record store is in memory here.** The runs use a throwaway store so that nothing is left
  behind; that the records survive a *file* store being closed and reopened is a unit test
  (`PersistenceTest.recordsSurviveARestart`), not something this engine run shows.
- **Two scenarios the plan lists have still never been run** - `TC-13` and `TC-16` - and the parts of
  the criteria that need a signed-in user remain unmet (`DEF-07`, `DEF-08`).
- **The engine is a local unsecured Camunda 8 Run**, with its own H2 store; nothing here says how the
  deployment would behave under load, on a cluster, or with authentication enabled.

WHAT THIS RUN ADDS
------------------
Everything else in this directory was produced against the Node.js
implementation of the workers. The workers have since been rewritten in Java,
and this is the first record made against that implementation. It covers all
three levels in one sitting and at one version: the configuration check, the
unit suite with no engine, and both engine runs.

The levels themselves are unchanged. The unit suite is still the same 38 cases
and still needs no engine; the engine runs are still the purpose-built linear
fixture and the delivered four `core-N` models with the eight forms. What is new
is the program under test: a Maven project on Java 21 rather than an npm project
on Node.js.

It is also the first engine record since a7f0dd6, which is the record it replaces
as the current one. The engine was available for this run, which is what the
c8556ba record could not have: that one was made on a machine with no engine
installed.

METHOD
------
1. `mvn clean` - the build directory was emptied first, so nothing below ran
   against a stale compilation.
2. `mvn compile exec:java -Dexec.args="--check"` - loads the configuration and
   reports the workers that would register, without connecting to an engine.
3. `mvn test` - the unit suite. The tests tagged `engine` are excluded from the
   default build, so this level needs no engine. They call the same handlers the
   workers call, with the simulated services running for real rather than mocked,
   so the ledger behaviour the duplicate checks rest on is exercised.
4. `mvn test -Pengine` - the engine runs. The profile selects the tests tagged
   `engine`, which both need Camunda 8 Run to be up.

Maven prints its own build progress before it reaches the tests - the plugin
versions, the resource copy, the compilation notices. Those lines are not
reproduced below; what follows is what each command printed from the
configuration check, or from the start of the test execution, to its final BUILD
SUCCESS line.

THE WORKERS ARE NOW JAVA
------------------------
The program under test is a Maven project on Java 21 using
`io.camunda:camunda-client-java`, pinned to the engine's own release so that the
client and the engine cannot drift apart. It serves the same six job types with
the same variables, error codes and outcomes as the Node.js implementation it
replaces, and a completed job still writes the same JSON log line, which the
refused-booking line above shows.

Three things could not be carried across unchanged, and each is deliberate:

- A failed job consumes one of the model's retries rather than setting them to
  zero. The Node SDK left an unset retry count out of the request, which reaches
  the broker as zero and raises an incident at once - the opposite of what
  `../../workers/README.md` describes. The wrapper now passes one fewer than the
  job currently has.
- The booking and payment ledgers make their check and their write together
  under a lock, because job workers are served by more than one thread here.
  Without it, two jobs for the same booking key could both find nothing and both
  write, which is the duplicate the ledger exists to prevent.
- The gateway is asked for its topology before any worker is registered, which is
  what the Node SDK's readiness callback used to provide. A worker that cannot
  reach the gateway now fails at startup instead of polling silently and taking
  no work.

None of the three is exercised by the runs above: the first two need a defect or
a race, and the third only shows itself when the gateway is absent. They are
recorded here because they are differences from the earlier evidence, not because
this run proves them. The retry behaviour in particular is only covered at the
handler level by the unit suite, which asserts that the wrapper leaves the count
to the client rather than setting it.

A MATTER OF RECORD, NOT A FAILURE
---------------------------------
The test names and the worker source comments still cite the earlier, coarser
allocation of rule and requirement IDs, exactly as they did before the rewrite:
a name such as "a request without clinical authorisation is not processed (TC-06,
BR-04, AC-02)" means BR-10 in the current list, and "(TC-04, BR-03)" means BR-07.
This was already true before this run; it is reported here because testing is
where it becomes visible. It is DEF-06 in ../test-plan.md, and the reconciliation
table at the top of ../../docs/requirements/requirements.md resolves each ID.

NOT COVERED HERE
----------------
- Anything needing a person. Every user task in every scenario above was
  completed by the run itself with the variables the scenario supplies, so the
  form contract is proved by the variables the model expects rather than by
  someone filling a form in (DEF-08). Thirty-six of the fifty-five user tasks
  bind no form at all, so for those there is no form to prove (DEF-13).
  Role-based access, task claiming and the audit trail cannot be exercised at all
  (DEF-07).
- TC-02, TC-13, TC-16 and TC-20 have no scenario in either engine run, as before.
- The exception branches not driven here: the between-cycle review's refusals,
  the suspected-clinical-error return in core-3, the another-appointment and
  pathway-review branches of the cancellation, and the no-slot-in-period case at
  model level. The unit suite covers the worker side of several of these.
- No incident was raised and no run drove the job-failure path through the
  engine, so the retry behaviour described above is unproven end to end.
- Stopping the workers with Ctrl-C was not exercised. The shutdown hook that
  closes the job workers, the client and the log is written, and the process
  starts, registers and takes work without it; no automated run has sent it a
  signal.
- `mvn test` on its own does not run the two engine levels. They are in the
  `engine` profile, selected with `-Pengine`, and a default build leaves them out
  entirely rather than reporting them as skipped - so a green `mvn test` says
  nothing at all about the engine levels. Within the profile, a run whose engine
  is not answering does report the seven as skipped, with the address it tried.
- The workers were exercised through this machine's engine only. The concurrency
  the ledgers now guard against is code that was read and reasoned about, not
  code that was reproduced under load.

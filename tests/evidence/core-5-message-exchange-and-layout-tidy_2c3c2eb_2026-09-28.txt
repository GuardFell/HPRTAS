WHAT THIS RUN ADDS
------------------
**The message a process waits for.** Nothing in the repository published a message with a
correlation key before this: the two messages `core-4` is started by are published without one,
because a message start event holds no subscription, and no model had an intermediate catch event
to wait at. `core-5-missing-information-message-exchange` adds the waiting side, the
`referral-document-request` worker adds the publishing side, and scenario 9 drives both.

Scenario 9 drives the negative half as well, which is the part that makes it evidence: a reply
correlated by a *different* referral is published first and the instance is asserted not to have
moved. The engine accepts a publication whose key no subscription is waiting on and correlates it
with nothing, so a scenario that published only the right key would pass whether or not the
correlation key did anything.

**Four repairs in the drawing tools.** Each one is visible in the exported diagrams: an
intermediate catch event had no shape at all (the kind was not named, so the waiting step - the
point of the model - was the one element missing from the picture, and the three flows through it
had no route); message flows are routed by a router of their own that knew about the shapes and
nothing else, so a dashed line ran through the words under an activity and along the top of a
sequence flow going the same way; crossing a label cost less than crossing a line, so the router
preferred to strike through a word; and an edge's middle was the only port offered, so a line
arriving from below was drawn straight through the activity's name.

The effect on `core-5`: no line crosses any label, no two lines run on top of each other, no message
flow passes through a shape, and the exported diagram reads back at 92% of its words by OCR rather
than 73%.

METHOD
------
1. `cd workers && mvn test` - the unit suite, no engine. It calls the same handlers the workers
   call, with the simulated services running for real.
2. `python tools/verify_hprtas_bpmn_bindings.py` - the contract between the models, the forms and
   the workers. It now also checks that the variable a message subscription is correlated by is
   written by a form or a worker in the same model.
3. `python tools/verify_hprtas_bpmn_layout.py` - the layout and BPMN rules, from the diagram
   interchange.
4. `python tools/verify_hprtas_bpmn_export.py` - renders each model and reads the words back with
   Windows OCR, which is the check that a label is actually legible in the export.
5. `cd workers && mvn test -Pengine` - the smoke fixture and the five delivered models, engine
   running. This deploys the models and the forms, so it changes what is in the engine.

purpose: `referral-validation` writes `requestedItems`, and it writes an empty list when it reports

refuse to publish. In the models the request step is fed by its own form.

WHAT THIS RUN DOES NOT COVER
----------------------------
- **No signed-in user submitted a form.** The user tasks were completed through the API, as the
  earlier records do. `DEF-08` in ../test-plan.md section 6 stands.
- **Authentication, role-based access and the audit trail are not implemented**, so nothing here
  exercises them. `DEF-07` stands.
- **The reply is published by the scenario, not by a worker.** `missing-information-supplied`
  belongs to the referring organisation, so no worker here sends it on the hospital's behalf; the
  scenario stands in for the participant that owns it.
- **The ledger duplicate guards are per worker process.** The simulated services keep their ledgers
  in memory, which is `DEF-10`.
- **The other six models were not laid out again.** The four repairs to the drawing tools take
  effect the next time a model is laid out, and only `core-5` was laid out for this change, so the
  committed exports of the other six diagrams are unchanged and still carry the message-flow
  routing this version fixes.
- **`tests/test-plan.md` still describes release-1.0.** Its counts and its section 4 rows are
  written per release; this record names its own version, and the plan needs its release row
  brought up to date when the next tag is cut.

    mvn test -Pengine                                   # deploys the models and the forms

The publication can also be made by hand, which is how a reader can watch the correlation key
matter:

    mvn compile exec:java -Dexec.args="--publish-message missing-information-supplied --correlation-key REF-2026-0001"

A name no deployed model declares, or a key no instance is waiting on, is accepted by the engine and
correlated with nothing, so the instance stays where it is and Operate is where to confirm it.

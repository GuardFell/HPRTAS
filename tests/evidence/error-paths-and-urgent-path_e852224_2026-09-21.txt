WHY THESE SCENARIOS
-------------------
Two defects had made parts of the models unreachable:

1. Camunda does not treat a sequence flow that has no condition as a fallback. An exclusive gateway
   whose conditionless "otherwise" flow is not declared with default="..." raises the incident
   "Expected at least one condition to evaluate to true, or to have a default flow" as soon as no
   condition matches. 21 gateways were in that state, so their otherwise branches could not be
   taken. Scenario 3 first reproduced this: it stopped at Gateway_SlotWithinWindow with that
   incident before the fix.

2. Four service tasks could raise INVALID_VARIABLE with no catch event, so the worker's business
   error became an incident. Scene 2 below is the exact input that produced an incident before the
   fix, recorded in referral-to-appointment_normal-path_1b42bff_2026-09-21.txt.

3. Gateway_UrgentReferral sent an urgent referral with no suitable slot straight back to the
   availability check, and the scheduling service answers the same way every time, so the case could
   only cycle. Scenario 3 drives the replacement path.

METHOD
------
1. deploy the three models from this commit
2. start the workers: `cd workers && npm start`
3. for each scenario: start an instance, complete each open user task through
   POST /v2/user-tasks/<key>/completion with the variables a validated form would supply, then read
   the path, the final state and the incidents collection back from the engine.
   forms/ is still empty, so the variables are passed with the completion call.

LIMITATIONS OF THIS EVIDENCE
----------------------------
- The variables are injected with the completion call because forms/ is empty. The forms must supply
  the same variables before release 1.0, and these scenarios have to be repeated without injection.
- Role-based access is not exercised: candidate groups are read back from the tasks, but no user is
  authorised and no task is claimed through Tasklist.
- Three of the six scenarios stop at the next human decision rather than at an end event, which is
  the expected state for a process waiting on a user task. Two end states are asserted as COMPLETED.
- The routes are exercised with the simulated services only, and one outcome per simulated service.
  The remaining alternatives (a slot outside the requested window, a declined payment, a treatment
  service that is unavailable) are covered at worker level in the other files in this directory.

Reproduce with:
  camunda-runtime\start-camunda.bat                     (wait for /v2/topology to return 200)
  curl -X POST "http://localhost:8080/v2/deployments" \
       -F "resources=@models/operational/referral-to-appointment.bpmn;type=application/xml"
  repeat the deployment for treatment-authorisation-and-booking.bpmn and
  clinic-letter-and-pathway-monitoring.bpmn
  cd workers && npm install && npm start
  then drive each scenario through POST /v2/process-instances and /v2/user-tasks/<key>/completion
